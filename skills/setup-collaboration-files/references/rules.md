# Init Project — 硬规则与归一原则

## 硬规则（Hard Rules）

### 入口与备份

1. 不要向用户抛出 `primary`、`template`、`backup` 之类参数选择；这个命令对用户只有一个入口。
2. 如果当前目录不是 git 仓库，只问一次：是否把当前目录当作项目根继续。
3. 检测到已有规则文件或协作文件需要重写，必须先备份到项目根，再按当前标准归一生成，不再额外询问。
4. 备份必须放在 `<repo_root>/setup-collaboration-files.backup/[YYYY-MM-DD_HHMMSS]/`。
5. 保留已有有效项目规则；重复信息去重；无法确定的冲突写 `[待人工确认]`。
6. 不伪造信息。提取不到就写 `[待补充]`。

### 一事实一归宿

7. 每个事实只有一个家：现状事实 → `docs/`；因果取舍 → `.agents/notes/`；命令速查 → `tools.md`；当前状态 → `memory.md`；常驻军规 → 根 `AGENTS.md`。
8. `tools.md` / `memory.md` 属协作辅助，不得覆盖正式设计真值。

### AGENTS.md 的分层与预算

9. 根 `AGENTS.md` 只放跨全仓规则；模块规则就近放子目录 `AGENTS.md`；子目录已有的规则不在根上复述。
10. 一条规则 1–3 行，讲完给链接；不写背景故事和长流程。
11. 字数预算（**缺省值**；仓库已有自己的预算文件或 CI 阈值时以仓库声明为准，不得用本文件的数字覆盖它）：根 `AGENTS.md` ≤1,950 词、子目录 `AGENTS.md` ≤750 词、`docs/architecture.md` ≤2,400 词、`docs/AGENTS.md` ≤1,320 词。超限按「下沉迁移 → 精简浓缩 → 申请提额」处理，不得靠删约束达标。
12. 归一结束后只允许有一个 substantive 的**全仓**规则文件：`AGENTS.md`。子目录 `AGENTS.md` 与 `docs/AGENTS.md` 是各自作用域内的规则，不算第二份全仓真值。
13. `CLAUDE.md` 只能是 `@AGENTS.md` 的兼容入口，不能作为第二份独立 substantive 规则文件；无论它原本是否存在，归一后都必须存在且只有这一行。
14. 结构、分层、依赖方向、关键入口、验证命令属于强制扫描填充项；不要直接生成空泛模板。
15. 文档优先级清单、项目特定禁令、模块特别规则只在仓库已有强信号时生成；不要臆造不存在的文档名、目录职责或禁令。
16. 每个 section 优先写仓库事实；确实提取不到时，单节最多写一条 `[待补充]`。
17. 空壳、占位或薄内容的已有文件必须在备份后重建，不能因为"文件存在"就跳过。

### docs/

18. `docs/` 只写当下事实：严禁「以前 / 现在 / 不再 / 改名为」这类变迁叙述。
19. 严禁人肉手抄由代码或 AST 能生成的清单（API 列表、配置表）；文档只圈定插槽。
20. 文档里的代码块必须能真实编译或运行通过。
21. `docs/postmortem/` 是全仓唯一允许写血泪史的地方；故障结论要沉淀成一行进根 `AGENTS.md`，不让战壕故事污染正常手册。

### .agents/notes/

22. 状态由目录位置决定：`proposed/`、`implemented/`、`rejected/`、`archived/`。
23. 严禁创建 `INDEX.md`、`notes/README.md` 或任何"每篇笔记都要改一行"的总索引——并行分支必然在那一个文件上冲突。
24. 已经发生的决定不能删：失效的旧笔记**结论不改**，只标注被哪一篇取代，并移入 `archived/`；严禁把旧笔记直接改写成新版本。
25. `archived/` 永久冻结，任何人不得修改。
26. `implemented/` 只写已经发生的事实，禁止 `## Proposal`、`## 计划`、`## TODO` 类标题。
27. 本技能不复述 `decision-notes` 的四格模板与非平凡判定表；`.agents/notes/AGENTS.md` 只写仓库不变量，写作方法由 `decision-notes` 拥有。
28. 骨架铺完而之后没人写笔记等于没铺：根 `AGENTS.md` 的笔记军规必须指名 `decision-notes` 技能。

### memory.md 与旧机制

29. `memory.md` 是持续滚动快照：完成一个完整功能/修复闭环后整体覆盖更新，不按每个小改动追加。
30. `memory.md` 只保留 `当前基线` / `已完成能力` / `进行中` / `仍需注意的坑点` / `最近活跃窗口`；不含"关键决策"节。目标 ≤120 行。
31. `memory.md` 初始化时 git 提交历史只作辅助线索；"已完成能力"必须是当前仓库仍成立的闭环能力，不能直接复制 commit 标题。
32. `memory/archive/` 属旧机制：已有文件保留不动、不再追加；仍在生效的因果条目建议迁入 `.agents/notes/`，事故内容建议迁入 `docs/postmortem/`，迁移由用户决定。

## 归一原则（Normalization Principles）

### 生成公式

`AGENTS.md` 必须由四类来源合成，而不是单一模板：

1. **常驻军规**
   - 放在文件最前，3–6 条，每条一行、可机械判定、附链接
   - 这是 agent 每次真正会读的部分，价值最高
   - 必须包含非平凡改动与决策笔记同批提交这一条
2. **固定协作骨架**
   - 注入这套协作体系必须有的规则：`tools.md` / `memory.md` 的读写时机、`.agents/notes/` 的不变量
   - 本命令的稳定基线，必须保留
3. **当前仓库事实**
   - 技术栈、目录职责、分层、依赖方向、关键入口、配置目录、标准验证命令
   - 优先来自当前代码、目录结构、manifest 和正式文档
4. **用户已有规则**
   - 仓库里已有 substantive 规则文件时，提取其中仍有效的项目规则
   - 重点继承：模块边界、真值源规则、项目特定限制、已有文档优先级、关键禁止事项

```text
AGENTS.md = 常驻军规 + 固定协作骨架 + 当前仓库事实 + 用户已有有效规则
```

### 信息使用优先级

不同类型的信息优先级不同，不要用一条全局优先级覆盖全部情况：

1. **协作记忆体系规则** — 以固定骨架为准；仓库已有写法更强且不冲突时可继承
2. **结构、技术栈、目录职责、入口、验证命令** — 以当前仓库事实和正式文档为准，不能被陈旧规则文件覆盖
3. **项目特定约束** — 优先继承已有 substantive 规则，再用正式文档和当前代码校验补强；仓库里没有就不要发明
4. **近期活动线索** — 只用于 `memory.md` 初始化或补强，不进入 `AGENTS.md` 的正式规则区

### 归一目标

- 一个 substantive 全仓 `AGENTS.md`
- 兼容入口 `CLAUDE.md`，恒为 `@AGENTS.md`（不存在则创建）
- 按作用域就位的子目录 `AGENTS.md`、`docs/AGENTS.md`、`.agents/notes/AGENTS.md`
- 不再保留两份互相独立、相互冲突的 substantive 全仓规则文件

### 各场景处理

| 场景 | 处理 |
|---|---|
| 只有 substantive `AGENTS.md` | 先备份，提取有效规则，按当前标准重写为 canonical，补齐缺失节，并新建指向它的 `CLAUDE.md` |
| 只有 substantive `CLAUDE.md` | 先备份，从 `CLAUDE.md` 提取有效规则生成 canonical `AGENTS.md`，`CLAUDE.md` 改写为 `@AGENTS.md` |
| `AGENTS.md` substantive + `CLAUDE.md` pointer | 先备份，以 `AGENTS.md` 为提取主源重写，`CLAUDE.md` 重写为 `@AGENTS.md` |
| `AGENTS.md` pointer + `CLAUDE.md` substantive | 先备份，以 `CLAUDE.md` 为提取主源生成新 `AGENTS.md`，再把 `CLAUDE.md` 改写为 `@AGENTS.md` |
| 两者都 substantive | 先分别备份，提取两边仍有效的规则，重复项留一份，冲突项参考正式设计与当前代码，仍无法确认写 `[待人工确认]`，合并产出一份 canonical `AGENTS.md` |
| 存在子目录 `AGENTS.md` | 不合并进根文件；检查其规则是否仍有效，失效的清掉，有效的原地保留，根上只留一行导航 |

### 抽取与改写原则

- 优先抽稳定、长期、跨会话仍成立的规则，不搬运临时任务说明或一次性操作步骤。
- 固定协作骨架负责"记忆体系如何长期工作"，不要把这部分交给临场发挥。
- 结构、分层、依赖方向、关键入口、验证命令优先从当前代码、目录和 manifest 生成。
- 已有 substantive 规则负责"这个项目原来就明确要求什么"，只要仍有效就继承而不是覆盖。
- 文档优先级清单、禁止事项、模块特别规则只在信号足够明确时拆出；缺信号时不发明。
- 现有规则已经很强时，不要硬压回薄骨架，可以保留为更多独立小节——只要最终仍然短、小、硬。

### 失效项的区分（本体系的核心纪律）

必须区分两类东西，处理方式相反：

| 类型 | 例子 | 处理 |
|---|---|---|
| **旧规则** | 已被正式文档或当前代码证明失效的约束、过时命令、废弃目录职责 | 归一过程中删除，不原样带入 |
| **已发生的决定** | `.agents/notes/` 里的条目、`docs/postmortem/` 的记录 | 一律不动；只标注被谁取代，不改结论 |

把这两类都当"过时内容"删掉，下个会话就会把已经被否掉的方案重新提一遍——这正是笔记体系要解决的问题。
